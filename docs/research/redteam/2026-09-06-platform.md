# Review: engine-core spec and slice-1 plan

Environment used: Xcode 27.0 (27A5194q), Swift 6.4, MacOSX27.0.sdk. Every claim below marked "verified" was checked by grepping the SDK headers/swiftinterface or by compiling the plan's code in a scratch package under `/private/tmp/.../scratchpad/pkgcheck` (nothing was written inside the repo).

## Blockers

None. The slice-1 plan's code, copied verbatim into a scratch package with the plan's `Package.swift`, builds cleanly in language mode 5, in language mode 6, and with `StrictConcurrency` enabled, and `swift test` runs Swift Testing from the CLI (Testing Library 2067.1).

## High

### H1. `FileHandle.write(_:)` in the download path crashes the process on I/O error
Spec, "Downloader and Verifier"; spike `Downloader.swift` line `handle.write(data)` (to be ported).
`write(_ data: Data)` is the legacy non-throwing API; on `ENOSPC`, `EIO`, or a USB reset (the Acer FA200 in memory hung exactly this way) it raises an ObjC `NSFileHandleOperationException`, which Swift cannot catch, so the harness dies mid-job with no job-store transition. Same for `handle.close()` after a late chunk. Fix: use the throwing API and a lock-guarded closed flag:

```swift
// inside dataReceivedHandler
state.withLock { s in
    guard !s.closed else { return }          // late chunk after cancel: drop it
    do { try handle.write(contentsOf: data); s.hasher.update(data: data); s.bytes += data.count; s.lastActivity = .now }
    catch { s.writeError = error; s.closed = true; manager.cancelDataRequest(id) }
}
```
and never `close()` the handle until the completion handler has fired or the post-cancel wait has expired, then mark `closed` first.

### H2. Read-back verification is served from the page cache, not the drive
Spec, "Downloader and Verifier": "`Verifier` then re-reads the file from the drive... only the read-back result counts (invariant 1)." Immediately after writing 4 GB, a re-read mostly hits the unified buffer cache, so the verifier is re-hashing RAM, and invariant 1 is nominal. Fix, cheap: after the last chunk, `fcntl(fd, F_FULLFSYNC)` (fall back to `fsync` when it returns `ENOTSUP`, which exFAT and SMB do), then open the read handle and set `fcntl(readFd, F_NOCACHE, 1)` before hashing. Cost on a USB SSD is ~10 to 20 s per 4 GB, well under the download time, so keep read-back rather than replacing it. On SMB, `F_NOCACHE` is honored by the client; still do it.

### H3. The Deleter/Restorer continuation pattern has a real data race and can double-resume
Spec "Deleter"/"Restorer" port spike `StageB.swift` `delete`/`restore`: `var resumed` is mutated from PhotoKit's completion queue and from `DispatchQueue.global().asyncAfter` with no synchronization. Two threads can both observe `resumed == false` and both call `cont.resume`, which traps in `withCheckedContinuation`. Compiling that exact code with `-swift-version 6` yields five `SendableClosureCaptures` diagnostics (mutation/reference of captured var in concurrently-executing code); it becomes an error when the package flips to mode 6. Fix with a one-shot box on `Mutex` (Synchronization, macOS 15+, verified compiles here):

```swift
import Synchronization
final class OneShot<T: Sendable>: Sendable {
    private let slot: Mutex<CheckedContinuation<T, Never>?>
    init(_ c: CheckedContinuation<T, Never>) { slot = Mutex(c) }
    func resume(_ v: T) { slot.withLock { c in c?.resume(returning: v); c = nil } }
}

func performChanges(timeout: Duration, _ block: @escaping () -> Void) async -> (Bool, Error?) {
    await withCheckedContinuation { cont in
        let once = OneShot(cont)
        PHPhotoLibrary.shared().performChanges(block) { ok, err in once.resume((ok, err)) }
        Task { try? await Task.sleep(for: timeout); once.resume((false, EngineError.message("performChanges timed out"))) }
    }
}
```
Do not capture `completionFired` or `placeholderID` as plain `var`s either; return them through the resumed value or read `placeholderForCreatedAsset` inside the change block into a `Mutex`.

## Medium

### M1. `ScanSummary.excluded` does not encode as a keyed object; the plan's text about macOS 27 is wrong
Plan Task 3 step 5: "on macOS 27 `String`-raw enums encode as dictionary keys without it." Verified false: `[ExclusionReason: Int]` encodes as `{"excluded":["notUserLibrary",2],"included":0}`. Round trip still passes, so the tests are green, but the JSONL summary is unreadable. Fix: add `extension ExclusionReason: CodingKeyRepresentable {}` unconditionally (verified: an empty conformance compiles and yields `{"notUserLibrary":2}`), and delete the "if it fails to compile" sentence.

### M2. `LocalityProbe` has no timeout and reads the whole file when local
Plan Task 5, spec "LocalityProbe". `withCheckedContinuation` with no watchdog hangs forever if the completion never fires (DTS-acknowledged PhotoKit bug in the feasibility doc; osxphotos wraps every request in 300 s for this reason). And for a local 4 GB original, the probe streams 4 GB through XPC just to learn "local". Fix: use the `OneShot` above with a 60 s timeout mapping to `.unknown`, and cancel on the first `dataReceivedHandler` chunk: a chunk arriving with network disallowed proves the bytes are local. After `cancelDataRequest` the completion may or may not fire (the header is silent; `PHPhotosErrorUserCancelled` 3072 is defined for exactly this), so treat "first chunk seen" as the answer regardless of what the completion later says, and keep the plan's `guard` semantics inside the box. The `var resumed` guard in the plan's version is not a race (only one closure touches it) but is also unnecessary.

### M3. `CLGeocoder` is deprecated in macOS 26; the spec targets macOS 27
Spec "MomentGrouper and PlaceNamer". `CLGeocoder.h`: `reverseGeocodeLocation` is `API_DEPRECATED("Use MKReverseGeocodingRequest", macos(10.8, 26.0))`. Replace with MapKit: `MKReverseGeocodingRequest(location:)` then `let items = try await request.mapItems` (the completion is `NS_SWIFT_UI_ACTOR`, so it hops to main; fine). No Location Services permission is needed for reverse geocoding (no `CLLocationManager`), only `com.apple.security.network.client`, which is already in the entitlements. Throttling surfaces as `MKError.loadingThrottled`; the spec's 1 req/s and 50-per-run ceiling are reasonable, and the cache key by rounded coordinate should persist across runs.

### M4. `PHAsset`/`PHAssetResource` are not `Sendable`; the spike's task-group pattern will not survive mode 6
Spec assumes porting spike `StageA.run()` (`group.addTask { await self.measure(v) }` with `PHAssetResource` flowing into tasks). `PHAssetResourceManager` is `NS_SWIFT_SENDABLE`; `PHAsset`, `PHAssetResource`, `PHFetchResult` are not. Under mode 6 every cross-task hand-off is an error. Design rule for slice 3: tasks receive `String` identifiers (or `AssetRecord`), and each task re-fetches its `PHAsset`/resource inside the task. PhotoKit objects are documented thread-safe, so an `@unchecked Sendable` wrapper is acceptable if re-fetch proves too slow, but identifiers are cleaner.

### M5. `scan()` cost is not "under one second"; that number measured the fetch only
Spec "LibraryScanner": "Under one second for 5,000 assets in the spike." The spike's `buildSweep` only enumerated `PHAsset`s. The plan's `facts(for:)` additionally calls `PHAssetResource.assetResources(for:)` for every asset, an XPC round trip to photolibraryd (typically several ms each), so a 5,300-asset scan is plausibly tens of seconds, on the main actor in the harness. Not wrong, but the spec claim is; the harness's `elapsedSeconds` will measure it. Consider running `scan()` off the main actor and, later, deferring resource lookup to plan time for assets that pass the `sourceType` filter.

### M6. Partial downloads land at the final path
Spec "Downloader": "Destination is the final path on the drive; there is no staging directory." A crash or power loss leaves `IMG_1234.MOV` that looks archived to a human (invariant 2), and resume must hash it to learn it is junk. Write `IMG_1234.MOV.partial` and rename after read-back verification; same volume, so the rename is atomic and free on APFS/exFAT/SMB.

### M7. Ad hoc signing (`make IDENTITY=-`) breaks TCC attribution on every rebuild
Plan Task 6 step 7: "run `make IDENTITY=-` to sign ad hoc; the sandbox still applies." True for the sandbox, but TCC stores a code-signing requirement with the grant. With the Apple Development identity (the spike is signed by "Apple Development: Dmitri Samoilov", team 83VCX8YH4U) the designated requirement is identifier + team certificate and survives rebuilds; the multiple B-bookmark runs minutes apart after rebuilds confirm this. Ad hoc signing yields a cdhash-based requirement, so every rebuild is a different app to TCC: expect a fresh prompt at best, and a stale record needing `tccutil reset Photos com.videoattic.ArchiveHarness` at worst. Reword: ad hoc is for a machine with no identity only, and requires `make reset-tcc` after each rebuild.

### M8. Deletion does not free library space for 30 days
Spec "JobState and JobStore" space planning counts the PhotoKit cache (finding 4) once, implying it is transient. Deleted assets sit in Recently Deleted for 30 days with no API to purge, so the cached originals stay on the boot volume after `deleted`. The budget model is correct for one job but the product must tell the user that internal space returns after 30 days (or manual emptying).

### M9. Security-scope lifetime across concurrent downloads
Spec "VolumeAccess": "`startAccessingSecurityScopedResource` is balanced with `stop` in a `defer` on every use." With 2 to 4 concurrent downloads, thumbnail generation, and a restore all touching the same volume URL, per-use start/stop pairs are fragile: a `stop` from one finished task can end access while another task's `FileHandle` is mid-write, and `AVAssetImageGenerator`/`PHAssetCreationRequest` need the scope alive until their completion fires (photolibraryd copies the file via a sandbox extension derived from the client's access). Simpler and safe: `VolumeAccess` starts once when the volume becomes `.available` and stops once when released or at exit; keep the URL object alive for the duration.

## Low

- L1. Plan `OutputFolder.obtain`: `_ = url.startAccessingSecurityScopedResource()` on a freshly panel-picked URL is unnecessary and the matching `stop` at exit may be unbalanced; harmless at exit, but the pattern should not be copied into `VolumeAccess`.
- L2. `open -W -a App --args ...`: if a previous harness instance is still running, LaunchServices activates it, the new arguments are dropped, and `-W` waits on the old process. The spike's `check-idle` guard exists for the Python tool only. Use `open -n -W` and a `pgrep -x ArchiveHarness` guard. Argument length is not an issue (ARG_MAX).
- L3. `includeHiddenAssets = true` (verified present, no availability guard): whether third-party PhotoKit clients actually receive hidden assets on macOS 27 with the locked Hidden album is undocumented. Hide one test video and compare `sweepCount` before/after in slice 1; the spec's "hidden included" assumption is otherwise untested.
- L4. `AVAssetImageGenerator` (slice 3): use `try await generator.image(at:)`, `appliesPreferredTrackTransform = true`, `maximumSize` 512, and `dynamicRangePolicy = .forceSDR` (macOS 15+), otherwise iPhone HDR/Dolby Vision posters come out washed out as JPEG. Works on security-scoped external files as long as the scope is held (M9). Reading the `moov` atom is random access; fine on USB, slow on SMB.
- L5. `progressHandler` for `.video` fires in roughly 0.1 steps but is not reliable as the sole activity signal: the spike logged `progress=1.0` and `progress=0.5,0.9` for some downloads. The spike's approach of touching `lastActivity` from both handlers is right; keep the 2 s poll but read the state under the lock (the spike reads `isFinished`/`lastActivity` unlocked, a race Swift 6 flags).
- L6. Inline SHA-256 is not a cost: CryptoKit `SHA256` runs above 1 GB/s on this hardware, an order of magnitude over USB throughput; chunk sizes are PhotoKit's (sub-MB to a few MB) and are not retained, so memory stays flat.
- L7. Plan `Makefile`: the release binary links `/usr/lib/swift/*` with `LC_RPATH @loader_path` only (verified with `otool`); no runtime bundling or extra rpath is needed, and no dylib products exist, so `cp` of the single binary is sufficient. `Info.plist` has every key required for `LSUIElement` + `NSApplication` accessory activation (the spike proves it).
